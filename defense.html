Call Me Maybe

Function calling in LLMs · constrained decoding · Qwen3-0.6B

One sentence: The program reads natural-language questions and writes back JSON saying which function to call and with what arguments — never the answer itself. The hard part is making a tiny 0.6B model produce reliable structured output. The technique that solves it is constrained decoding: at every token step, mask any illegal token with −∞ so the model can only pick legal ones.

The single most important insight: The JSON braces are never written by the model. Python builds a dict and calls json.dump. The model only supplies values (function name, numbers, strings). So 100% valid JSON is free; constrained decoding makes the values correctly typed.

What goes in and out

Input 1 — Catalog

data/input/functions_definition.json lists every function the model may call (name, description, parameter types, return type).

Input 2 — Prompts

data/input/function_calling_tests.json lists the natural-language prompts to process.

Output

data/output/function_calling_results.json — one entry per prompt with prompt, name, parameters.

🧠 The 8 Foundational Concepts

These are the questions evaluators ask. Master them and you've passed the hardest part of the defense.

1Tokens & the vocabulary

An LLM does not read words or letters. It reads tokens — small text chunks. "hello" → 1 token; "fn_add_numbers" → ~3 tokens; "42.0" → 4 tokens. Qwen3 has ~151,936 tokens.

A numbered LEGO catalog. Every brick has an ID. The model builds sentences only out of bricks from the catalog.
LLM.encode(text) → list of IDs. LLM.decode(ids) → text. The Vocab class decodes every ID once at startup.
A token is a chunk of text — word, subword, character, or punctuation — that the tokenizer extracts via BPE. Each has a unique integer ID. Qwen3's vocabulary has about 152,000 tokens.

2Generation is a loop, not a sum

Most-misunderstood point. The model outputs scores for the next token; you pick one, append it, and ask again. That's generation:

# Generation loop (this is what generate_number / generate_string do)
for _ in range(max_tokens):
    logits = llm.logits_after(prefix)       # step 1
    best   = _argmax_in(logits, allowed)    # step 2 (constrained)
    out.append(best)                        # step 3
    prefix.append(best)                     # step 4
    if stop_condition: break          # step 5
Predictive text on your phone, but with 152k options and you control which one gets accepted.
Generation is a loop: feed prefix → get logits → argmax → append → repeat. Summing log-probs is a different operation — it's for comparing fixed candidates (like 'true' vs 'false'), not for generating new text.

3Logits — raw scores

The ~152k numbers the model outputs are called logits. They are raw and unnormalized, not probabilities. Typically range −15 to +25. Higher = more plausible. They do not sum to 1.

Judges' raw scorecards before any conversion to percentages.
A logit is a raw, unnormalized score the model assigns to each vocabulary token as a candidate for the next position. It's not a probability. Higher = more plausible.

4argmax vs max

max(logits) returns the highest value; argmax(logits) returns the index. We want the index because the index IS the token ID. Token ID 17 is "dog"; the number 7.5 is just a score.

Python has no built-in argmax. The idiom:

top = max(range(len(logits)), key=lambda i: logits[i])
max gives the prize; argmax gives the winner. We need the winner.

5Softmax — and why you skip it

Softmax turns logits into probabilities: prob[i] = exp(logit[i]) / Σ exp(logit[j]). Key property: it preserves order. So argmax(logits) == argmax(softmax(logits)). Your code never computes softmax when it just needs the winner.

Softmax converts logits into probabilities in [0,1] that sum to 1. I don't compute it because it preserves ordering — argmax on raw logits picks the same token.

6Log-probabilities — and summing them

To compare whole sequences (like "true" vs "false") you need their probabilities. Multiplying many small probabilities underflows. Logs turn multiplication into addition:

log P(sequence) = log P(t1) + log P(t2|t1) + log P(t3|t1,t2) + ...

So you sum log-probs to score a candidate.

Sum of log-probs = log of the product of probabilities = log P(sequence) — the model's actual likelihood of generating that candidate. That's the quantity to maximize. Raw logits are unnormalized, so summing them biases toward long candidates; log-probs are normalized.

7log-sum-exp — the safe denominator

exp(700) overflows to infinity. To compute log(Σ exp(values)) safely:

m = max(values)
return m + math.log(sum(math.exp(v - m) for v in values))

Subtract the max so the largest exp is exp(0) = 1; add it back at the end. Same result, no overflow.

Numerical stability trick. Without it, exp of a large logit can overflow. Subtracting a constant from every term and adding it back doesn't change the result.

8Masking with −∞ — this IS constrained decoding

Set illegal tokens' logits to −∞. Then argmax can never pick them, and after softmax their probability is exp(−∞) = 0. Why not 0? Because 0 is a perfectly normal logit value (many good tokens score near 0) — it wouldn't suppress an illegal token.

Your code does this cheaper: _argmax_in(logits, allowed) just searches the maximum among allowed IDs — mathematically identical to masking, without building a 152k-long array.

A multiple-choice test where someone crosses out wrong answers before you choose — you can't pick them.
Three places I use it: function-name selection, number generation, and string Stage B (substring fallback). The primitive is _argmax_in; it's equivalent to setting other logits to −∞ and taking argmax, but cheaper.

🐍 Pydantic — from zero

Pydantic is a Python library for data validation using type hints. It turns "type hints are suggestions" into "type hints are runtime rules."

In plain Python, type hints are ignored at runtime. Pydantic flips this: it uses the same hints as runtime validation rules. Data that doesn't match raises ValidationError.

The four superpowers

1. Validation

Model.model_validate(dict) — turns a dict into a typed object or raises ValidationError.

2. Coercion

{"age": "30"} becomes age=30 — smart conversion.

3. Attribute access

obj.name instead of data["name"]. Your IDE autocompletes.

4. Serialization

model.model_dump() — back to a plain dict for json.dump.

The three methods you actually use

# 1. Parse — io_utils.py
fn = FunctionDef.model_validate({"name": "fn_add_numbers", ...})

# 2. Construct — __main__.py
call = FunctionCall(prompt=..., name=..., parameters=...)   # validates too

# 3. Serialize — io_utils.save_function_calls
data = [call.model_dump() for call in calls]
json.dump(data, f, indent=2)

⚠️ Old tutorials use parse_obj / dict() — those are Pydantic v1. You use v2: model_validate / model_dump.

All data classes use BaseModel per the subject. LLM and Vocab are not data classes — they're behavior wrappers (the SDK firewall and the vocab cache). Pydantic doesn't apply to those.

models.py — the contract

Declares four Pydantic shape templates so the rest of the code receives typed, validated data instead of raw dicts.

from typing import Any, Literal
from pydantic import BaseModel

ParamType = Literal["number", "integer", "string",
                    "boolean", "array", "object"]

class TypeSpec(BaseModel):
    type: ParamType

class FunctionDef(BaseModel):
    name: str
    description: str
    parameters: dict[str, TypeSpec]
    returns: TypeSpec

class TestPrompt(BaseModel):
    prompt: str

class FunctionCall(BaseModel):
    prompt: str
    name: str
    parameters: dict[str, Any]

What to remember

  • Literal[...] whitelists exactly those six strings — better than str (which would accept "wibble").
  • FunctionDef.parameters is dict[str, TypeSpec] → declared types.
  • FunctionCall.parameters is dict[str, Any] → actual values.
  • Pydantic validates nested models recursively.

io_utils.py — disk + JSON bridge

Three functions. Two read (one per input file), one writes. Every reader runs the same defensive pattern: exists → parse → shape-check → schema-validate, translating four failure modes into two clean exceptions.

def load_function_definitions(path: Path) -> list[FunctionDef]:
    if not path.exists():
        raise FileNotFoundError(f"Function definitions file not found: {path}")

    try:
        with path.open("r", encoding="utf-8") as f:
            raw = json.load(f)
    except json.JSONDecodeError as e:
        raise ValueError(f"Invalid JSON in {path}: {e}") from e

    if not isinstance(raw, list):
        raise ValueError(f"{path} must contain a JSON array...")

    try:
        return [FunctionDef.model_validate(item) for item in raw]
    except ValidationError as e:
        raise ValueError(f"Schema error in {path}:\n{e}") from e

Key ideas

  • with = context manager. Guarantees file close even on exception. Subject mandates this.
  • raise ... from e = exception chaining. Translate types without losing debug info.
  • Only two exception types come out: FileNotFoundError or ValueError. __main__.py catches both in one line.
  • save_function_calls uses path.parent.mkdir(parents=True, exist_ok=True) — like mkdir -p, never crashes if dir exists.

__main__.py — the CLI & main loop

The entry point. Parses CLI args, loads inputs (the only try in the project), builds the LLM + vocab cache, loops over prompts, writes output.

def main() -> int:
    args = parse_args()

    try:
        functions = load_function_definitions(args.functions_definition)
        prompts   = load_test_prompts(args.input)
    except (FileNotFoundError, ValueError) as e:
        print(f"[error] {e}", file=sys.stderr)
        return 1

    llm   = LLM()
    vocab = Vocab(llm)

    results: list[FunctionCall] = []
    for i, p in enumerate(prompts, 1):
        chosen = pick_best_function(llm, p.prompt, functions)
        params = fill_parameters(llm, vocab, p.prompt, chosen)
        call   = FunctionCall(prompt=p.prompt, name=chosen.name,
                              parameters=params)        # 3rd Pydantic check
        results.append(call)

    save_function_calls(args.output, results)
    return 0

if __name__ == "__main__":
    sys.exit(main())

Things to know

  • The try here is the only one in the whole project. Clean error model.
  • Errors print to stderr (not stdout) — convention.
  • Building FunctionCall(...) validates a third time (in addition to the two in io_utils).
  • The if __name__ == "__main__" guard is the standard Python entry idiom.

llm_runner.py — the heart

Holds everything interesting: the LLM wrapper (forbidden-import firewall), the vocab cache, and the constrained-decoding logic for stage 1 (function selection) and stage 2 (per-type generation).

Math helpers

def _logsumexp(values: list[float]) -> float:
    m = max(values)
    return m + math.log(sum(math.exp(v - m) for v in values))

def _argmax_in(logits: list[float], allowed: set[int]) -> int | None:
    best_id, best_score = None, float("-inf")
    for tok in allowed:
        if logits[tok] > best_score:
            best_score, best_id = logits[tok], tok
    return best_id

_logsumexp = stable Concept 7. _argmax_in = the masking primitive (Concept 8): equivalent to setting outside logits to −∞ and taking argmax, but cheaper.

The LLM wrapper

class LLM:
    def __init__(self, model_name="Qwen/Qwen3-0.6B"):
        self._sdk = Small_LLM_Model(model_name=model_name)

    def encode(self, text):       return self._sdk.encode(text).tolist()[0]
    def decode(self, ids):         return self._sdk.decode(ids)
    def logits_after(self, ids):   return self._sdk.get_logits_from_input_ids(ids)
    def vocab_size(self):
        return len(self.logits_after([0]))     # logits length = vocab size

Why this exists: subject forbids torch / transformers. SDK uses both. This class converts every SDK call to plain Python types so the rest of the code never sees a tensor.

The Vocab cache

class Vocab:
    def __init__(self, llm):
        self.size = llm.vocab_size()
        self.id_to_text = {i: llm.decode([i]) for i in range(self.size)}

    def tokens_where(self, predicate):
        return {i for i, txt in self.id_to_text.items() if predicate(txt)}

Decode 152k tokens once at startup (~10s). Then filtering by predicate (e.g. "all numeric tokens") is a fast set comprehension.

Stage 1 — function selection

Encode the selection prompt, ask for next-token logits once, rank candidates by their first-token logit. If candidates share a first token (which happens with the fn_ prefix), fall back to full sum-of-log-probs scoring via score_candidate.

Stage 2 — per-type generators

  • generate_number — allows only digit/./- tokens; stops when the unconstrained top is non-numeric.
  • generate_string — Stage A: allow any non-empty token, stop on newline. Stage B (fallback): force substring of user prompt.
  • generate_boolean — score "true" vs "false" with score_candidate, pick higher.

The dispatcher

def fill_parameters(llm, vocab, user_prompt, fn_def):
    result = {}
    defaults = {"integer": 0, "number": 0.0, "boolean": False}
    for param_name, type_spec in fn_def.parameters.items():
        prompt  = build_param_prompt(user_prompt, fn_def, param_name, result)
        context = llm.encode(prompt)
        try:
            if type_spec.type == "number":
                result[param_name] = generate_number(llm, vocab, context)
            elif type_spec.type == "integer":
                result[param_name] = generate_number(llm, vocab, context, is_integer=True)
            elif type_spec.type == "boolean":
                result[param_name] = generate_boolean(llm, context)
            else:
                result[param_name] = generate_string(llm, vocab, context, user_prompt)
        except ValueError:
            result[param_name] = defaults.get(type_spec.type, "")
    return result

Never-crash guarantee: if generate_number raises, the typed default keeps the output JSON valid.

⚠️ Three honest risks to know

Old documentation contained over-confident claims. Knowing the truth makes you sound mature — not weaker.

1. The "first-token speedup" may not fire on your data

Old README claimed "no collisions, exact, 15× speedup." But all your function names start with fn_, so they likely share the same first token → the tie-breaker (full scoring) runs every time.

Defense answer: "My picker reads next-token logits once and ranks by first-token logit. When candidates share a first token, I fall back to sum-of-log-probs. In my test data, all names start with fn_ so the tie-breaker runs every time. The optimisation is general; correctness is preserved either way."

2. Stage A string generation isn't strongly content-constrained

Old DEFENSE claimed "the model can never write a }." That's only true for Stage B (the substring fallback). Stage A allows any non-empty token; it just stops on a newline.

Defense answer: "Strings can't be enumerated like digits, so my constraint is the boundary, not the content. Stage A allows any non-empty content token and stops on newline. JSON validity is guaranteed by json.dump, not by the model — the model only supplies the string value."

3. numpy is declared but unused

It's in pyproject.toml but never imported.

Defense answer: "Allowed by the subject; declared for potential extension. The current algorithm uses plain Python lists, which are fast enough."

Constrained decoding

_argmax_in(logits, allowed) is the primitive. Three uses: (1) function-name selection — allowed = candidates' first tokens; (2) generate_number — allowed = digit/./- tokens; (3) generate_string Stage B — allowed = tokens keeping the value a substring of the user prompt.
It searches the maximum only among allowed IDs. Mathematically equivalent to setting other logits to −∞ and taking argmax, but cheaper because no 152k array is materialised.
Priming. The model has seen millions of key = 'value'\n patterns. Ending with key = ' puts it in string-literal mode; its natural continuation is the value, a closing ', and a newline.

Architecture

We filter the vocabulary by predicate many times. Decoding 152k IDs once at startup costs ~10s; subsequent filters are fast set comprehensions.
Subject forbids import torch / transformers. The SDK uses them internally. The wrapper converts every SDK call to plain Python types so the rest of the code never sees a tensor.
Subject mandates it for data classes. It gives free schema validation at every JSON boundary, with clean ValidationErrors.
Speed. Naive scoring of every candidate's full sequence costs n×~3 forward passes per prompt. First-token uses one. When first tokens collide — as they do with the fn_ prefix in my data — the tie-breaker takes over. Correctness preserved.

Error handling

io_utils.load_function_definitions raises FileNotFoundError; __main__.py catches, prints [error] ... to stderr, exits 1. No crash.
generate_number raises ValueError. fill_parameters catches and falls back to a typed default (0.0, 0, False, "") so we still write a valid FunctionCall.
Three places: (1) io_utils.load_function_definitions; (2) io_utils.load_test_prompts; (3) __main__.py when constructing each FunctionCall(...).

Subject requirements

Every file open uses with path.open(...) as f: — io_utils.load_* and save_function_calls.
Every function has return + parameter types; every function and class has a PEP 257 docstring.
It's allowed by the subject; declared for potential extension. The current algorithm uses plain Python lists, which are fast enough.

One last thing to memorize — your 60-second elevator pitch

"The project takes a sentence like 'What is the sum of 2 and 3?' and produces a structured JSON call: {name: fn_add_numbers, parameters: {a: 2.0, b: 3.0}}. The hard part is making this reliable with a tiny 0.6B Qwen3 — asked nicely for JSON it succeeds only about 30% of the time. The technique I use to push that to ~100% is constrained decoding: at every token step, I look at the model's logits for all 152,000 vocab tokens and forbid any that would break the type I expect. The pipeline is two stages — function selection by first-token logit with a sum-of-log-probs tie-breaker, then per-parameter type-specific generation (digits-only for numbers, boundary-on-newline for strings with a substring fallback, scored 'true' vs 'false' for booleans). The JSON itself is built by Python with Pydantic and written with json.dump — never by the model. That's why 100% valid JSON comes for free; constrained decoding makes the values correct, not the braces."
